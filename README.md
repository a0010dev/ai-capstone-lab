# Industrial Reporting Agent

A read-only reporting agent over company data, built as an AI Engineering Buildcamp capstone project. It helps industrial company users answer business questions while keeping data access and calculations controlled and deterministic.

## The Problem

When industrial company users need information that is not covered by an existing report, they often have to describe their needs to IT, which retrieves the data and builds a report. This project aims to let users ask those questions directly and receive reliable answers from company data.

## What It Does

The agent interprets business questions and uses approved, read-only tools. The current backend queries synthetic inspection records; a future backend will query the company API. The tools control data access and perform deterministic calculations; the agent returns an answer with relevant totals and supporting detail.

For example, a user might ask: “Show the recorded affected-board quantities for TE and TV in September 2026,” then “And in October?” The UI carries forward the sections, year and metric. Production totals and validated defect rates are not currently available: inspected sample quantities must not be presented as total production, and error occurrences must not be labelled as affected boards.

Existing report requests and their expected results will form an evaluation set to test whether the agent returns the information users actually need and matches the established calculations.

## Streamlit app

Launch the industrial reporting chat from the repository root:

```sh
uv sync
uv run streamlit run app.py
```

Set `OPENAI_API_KEY` in `.env`; `OPENAI_MODEL` optionally overrides
`gpt-4o-mini`. The app uses the existing reporting agent unchanged and queries
only the synthetic fixture. Questions make real model API calls.

The Catalan interface keeps session chat history, shows an expanded tool trace
with arguments and results as tools execute, and displays the model,
reference date (Europe/Madrid), and source dataset. Related-question buttons
reuse the section and explicit dates from a single successful selection.
The sidebar clears both the displayed history and the context sent to the model.
Sections, periods and metrics can be carried forward in follow-ups and short
clarification replies during the same session.

The Streamlit entry point runs the asynchronous agent with `asyncio.run`:
text appears progressively with a cursor, and tool activity updates live.
The final answer replaces provisional text and removes the cursor. Tool traces
remain visible after reruns. If a stream fails, partial answer text is discarded
and the error and available tool activity persist without repeating the request.
The UI displays source metadata rather than confidence scores. No search index is needed.
The history sent to the model includes questions, assistant outputs and completed
tool calls/results. Related questions are deterministic shortcuts built from the previous selection, rather than
follow-up questions generated by the model. No index cache is required for
the small local JSON fixture.

Run the UI checks without model calls:

```sh
uv run pytest tests/test_app.py -q
```

The remote query requires the read token and searches the last two days (UTC).
Unlike the course's PydanticAI `trace_replay`, it returns span data directly;
it does not attempt to reconstruct a PydanticAI `AgentRunResult` from this custom
runtime. Traces contain prompts, answers and tool data; the current backend is
synthetic.

A default `run_agent()` call creates one session covering the whole query,
including all model rounds and tools. Streamlit uses this boundary per submitted
question and displays its usage estimate and trace ID. Conversation history
continues to work, but a Streamlit conversation is not one continuous trace.
To group multiple awaited turns under one trace with cumulative session costs:

```python
from est_prog.capstone_reporting.agent import run_agent
from est_prog.capstone_reporting.monitoring import monitoring_session

# Inside an async function:
with monitoring_session(model="gpt-4o-mini") as session:
    first = await run_agent("Resum de TE de setembre de 2026")
    second = await run_agent("I a l’octubre?", message_history=first["message_history"])
print(session.as_dict())
```

The accumulator adds each API response's `usage.input_tokens` and
`usage.output_tokens` exactly once, in both streaming and non-streaming paths.
It retains known usage when a later step fails. Missing usage or an unpriced
model produces an unknown estimate (`None`), rather than a misleading zero.
One grouped session uses one model.

For `gpt-4o-mini`, the rate table uses $0.15 per million input tokens and $0.60
per million output tokens, verified against the
[OpenAI model pricing](https://developers.openai.com/api/docs/models/gpt-4o-mini)

batch discounts; it is not an invoice reconciliation. The trivia homework's

## Week 3: tool-calling agent

Three deterministic tools are implemented: `get_defect_summary` for totals,
`get_defect_detail` for source controls and defect rows, and `get_defect_pareto`
for ranking defect codes by a selected metric. All three take `section`,
`date_from`, and `date_to`, and return the applied filters,
synthetic source, and provisional metric semantics. A document search tool
would not add value for these structured reporting queries.

`est_prog/capstone_reporting/agent.py` adds a Python 3 Responses API loop over
these functions, following the [official function-calling protocol](https://developers.openai.com/api/docs/guides/function-calling).
The model selects tools; an allowlisted dispatcher validates the arguments,
executes the functions, and returns their results to the model. The loop keeps
a tool trace and stops after at most eight model rounds. The original RAG
notebook remains available as a baseline; the deterministic backend has no
OpenAI dependency. This capstone requires Python 3.13 or later. Python 2.7 is
a constraint of the external ERP environment, not a local runtime or test requirement.

Open notebook 04 and run all cells with `OPENAI_API_KEY` configured in `.env`.
It uses the baseline model `gpt-4o-mini`; set `OPENAI_MODEL` to override it.
Running the notebook makes paid API calls. The evaluation fixes the reference
date at `2026-10-16` to make relative-month queries reproducible.

```python
import asyncio
from dotenv import load_dotenv
from est_prog.capstone_reporting.agent import run_agent

load_dotenv()
result = asyncio.run(run_agent("Show the defect summary for TE in September 2026."))
print(result["answer"])
print(result["tool_calls"])
```

In Jupyter or another async function, use `await run_agent(...)` instead of
`asyncio.run`. `run_agent` and `execute_tool` are now coroutine functions.
The OpenAI client is `AsyncOpenAI`; internally created clients are closed when
the run finishes, fails or is cancelled. A caller-supplied async client remains
the caller's responsibility.

`est_prog/capstone_reporting/tools.py` exposes the three awaitable reporting
tools. It currently delegates fixture file access to `asyncio.to_thread`.
The deterministic functions in `defects.py` and the package's root exports
remain synchronous for offline analysis and the terminal demonstration. A
future API backend can implement awaited HTTP requests behind the tool signatures;
no real ERP/API connection is configured yet. Model rounds and tool calls retain
their existing order; async does not automatically introduce parallel queries.

Without `message_history`, a call starts a fresh conversation. For follow-ups,
pass the previous result's `message_history`, as Streamlit does. API failures propagate;
invalid tool arguments are returned to the model for correction. No matching
records do not establish zero production or complete data coverage. Rates
and job aggregation remain unsupported until their definitions and
dedicated deterministic tools are validated. Natural-language answers still
need review against the traces; the notebook checks routing, filters and facts,
not every claim in the prose. No ERP connection is made.

`tests/test_judge.py` adds a course-style `assert_criteria` evaluation using the

Structured output follows the
[official OpenAI documentation](https://developers.openai.com/api/docs/guides/structured-outputs).

Set `OPENAI_JUDGE_MODEL` to override the judge's default `gpt-4o-mini` independently

Before evaluating agent changes, calibrate the judge with fixed answers:

```sh
# Six fixed examples, twice each: 36 judge calls, no reporting-agent calls.
uv run pytest tests/test_judge_calibration.py -v -s
```

`tests/fixtures/judge_zero_removals.json` stores fixed tool evidence, answers,
and human-assigned C1/C2/C3 labels. Cases include correct answers without
percentages, undefined percentages, the historical missing-records error,
an incorrect numeric percentage, an unsupported defect rate, and a wrong
end date. Expected labels are never sent to the judge. The shared rubric in
`tests/judge_criteria.py` explicitly accepts answers that omit percentages.

This small calibration set checks known failure modes; it does not establish
general judge accuracy. It follows the principle of calibrating automated
scores against human labels in the
[official OpenAI evaluation guidance](https://developers.openai.com/api/docs/guides/evaluation-best-practices).

The agent instructions now distinguish a nonempty zero-total Pareto from an
empty result, require a summary before interpreting an empty Pareto, and reserve
unknown-coverage wording for a summary with zero matching controls. The
[calibration and correction report](submissions/week4-judge-improvements.md)

## Async migration

The migration changes execution, while preserving the existing queries, tool
schemas, metric definitions, criteria and answer/trace result shape. The agent,
tool dispatcher and judge helpers must be awaited. Streamlit is the synchronous
boundary; it creates a fresh event loop per query and does not cache async clients
between reruns. The async migration itself did not add streaming or memory;
streaming and optional session context have since been added as described below.

## Streaming responses and tool activity

Supply an async `on_event` callback to `run_agent` to stream Responses API text
and report tool execution while retaining the same final result. Streamlit
enables this mode. Callers without a callback continue to receive a completed
result through the non-streaming request path.

```python
async def show_event(event):
    if event["type"] == "text_delta":
        print(event["delta"], end="", flush=True)
    elif event["type"] == "tool_start":
        print("\nTool:", event["name"], event["arguments"])

result = await run_agent(question, on_event=show_event)
```

| Event | Fields | Meaning |
|---|---|---|
| `round_start` | `round` | A new model round begins; reset provisional answer text. |
| `text_delta` | `round`, `delta` | Append newly received text for this round. |
| `tool_start` | `call_id`, `name`, `arguments` | The complete call is ready and the tool is about to execute. |
| `tool_end` | `call_id`, `call` | The tool finished; `call` has the same shape as a trace entry. |
| `completed` | `result` | The validated complete response and trace, also returned by `run_agent`. |

Text in rounds that call tools is provisional. The UI replaces it on the next
round; only the final assembled answer is saved as a completed answer. Complete
SDK output items, including reasoning context and function-call IDs, are reused
for the next model round. SDK-only `parsed`/`parsed_arguments` fields are removed
before sending those items back to the API. Tools never execute partial argument
fragments. Streams and owned clients close on errors, cancellation and callback
failures, and failed runs never emit `completed`.

```sh
# Streaming protocol and UI regression, without API calls.
uv run pytest tests/test_streaming_agent.py tests/test_app.py -m "not integration" -q

# Actual streamed tool call and text fragments; incurs API usage.
uv run pytest tests/test_streaming_agent.py -m integration -v -s
```

The implementation follows the [Responses streaming guide](https://developers.openai.com/api/docs/guides/streaming-responses).
The [streaming report](submissions/streaming.md) preserves validation and the
API protocol issue found during the first live check.

## Conversation context

```python
first = await run_agent("Mostra les plaques afectades de TE i TV de setembre de 2026.")
second = await run_agent("I a l'octubre?", message_history=first["message_history"])
```

The result now also includes replayable `message_history`. The agent copies
caller-provided history, appends the current question once, and preserves
assistant messages, reasoning context, tool calls and tool outputs in order.
The current turn's `tool_calls` still contains only that turn's calls. Requests
continue using `store=False`; the application manages context explicitly rather
than using server-side response IDs.

Streamlit keeps this state per session, including clarification turns, and
clears it with the conversation. Failed requests retain the question and a
generic error in session context but never replay unfinished tool calls or
partial answer text. Existing UI sessions can recover their visible transcript;
old assistant wording is not evidence of correct metric meanings, so operational
facts must still be supported by tools.

The state is in session memory, not durable storage across devices or sessions.
History grows with the conversation; there is currently no summarization or
automatic truncation. Other API callers and integration fixtures remain independent
by default unless they explicitly pass history. The original week 4 tests and
reports describe the earlier independent-query design.

```sh
uv run pytest tests/test_conversation.py -m "not integration" -q
uv run pytest tests/test_conversation.py -m integration -v -s
```

The [conversation-context report](submissions/conversation-context.md) records
validation and remaining model limitations. History handling follows the
[official Responses conversation-state guide](https://developers.openai.com/api/docs/guides/conversation-state).

## Defect Pareto

```python
from est_prog.capstone_reporting import get_defect_pareto

pareto = get_defect_pareto(
    section="TE", date_from="2026-09-01", date_to="2026-09-30",
    metric="removed_boards",
)
```

Allowed metrics are `errors`, `affected_boards`, `repaired_boards`, and
`removed_boards` (the default). The response includes the common metadata,
`metric`, `total_quantity`, and `items` ranked by descending quantity, with
ascending defect codes breaking ties. Each item includes its quantity, share,
cumulative share, and original job/control/record references. Shares are
contributions to the selected metric, not defect rates or evidence of causes.
Percentages are unrounded; zero totals produce `null` percentages and retain
observed codes and source rows. No defect rows produces an empty list.
For TE in September 2026, removals rank C=8, A=3, B=1 (total 12).
The Python function defaults to `removed_boards`; the agent's strict tool
schema requires an explicit `metric` and instructs the model to select that
default when the user does not specify one.
